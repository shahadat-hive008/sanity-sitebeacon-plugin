# AGENTS.md

## 1. Project Overview

We are building a reusable Sanity Studio plugin named **Sitebeacon Analysis**.

The plugin will provide a dashboard inside Sanity Studio for viewing website analysis reports, performance metrics, accessibility information, SEO-related results, and resource data supplied by Sitebeacon.

The implementation will begin with mock data. Real Sitebeacon API integration will happen after the available API endpoints, response structure, authentication requirements, and pagination behavior have been verified.

### Project References

* Payload reference implementation: https://github.com/siam-lh/Payload-Sitebeacon-Plugin-Template
* Sanity Lighthouse reference: https://github.com/Halo-Lab/sanity-lighthouse-plugin
* Official Sanity plugin development documentation: https://www.sanity.io/docs/studio/developing-plugins
* Official Sanity custom Studio tools documentation: https://www.sanity.io/docs/studio/custom-studio-tool

Treat reference repositories as sources of ideas, not code that must be copied unchanged. Confirm the compatibility, licensing, architecture, and relevance of any code before reusing it.

## 2. Primary Goals

* Build a reusable and maintainable Sanity Studio plugin.
* Provide a clear dashboard for website analysis reports.
* Use mock data to develop and test the UI independently of the real API.
* Keep data access separate from presentation components.
* Handle missing, nullable, incomplete, pending, and failed report data safely.
* Make the real API provider replaceable without rewriting the dashboard.
* Document installation, configuration, development, testing, and publishing.
* Keep the plugin suitable for production use.

## 3. Scope and Non-Goals

### In Scope

* A custom Sanity Studio tool.
* Report and metric types.
* Mock report fixtures and a mock data provider.
* Dashboard and report-detail components.
* Desktop/mobile metric presentation where supported by the data.
* Loading, empty, error, and partial-data states.
* Search, filtering, pagination, and refresh where appropriate.
* Unit and component tests.
* Future integration with the real Sitebeacon API.
* Package documentation and release preparation.

### Not Assumed Yet

* The final Sitebeacon API endpoint structure.
* The final authentication mechanism.
* Whether every report has desktop and mobile results.
* Whether search and pagination are client-side or server-side.
* The meaning of undocumented fields or abbreviations.
* Whether analysis data should be stored in Sanity documents.

Do not implement these assumptions as facts. Verify them before finalizing the relevant feature.

## 4. Architecture

Keep the plugin organized around clear responsibilities.

* **Studio tool:** Registers the Sitebeacon Analysis interface in Sanity Studio.
* **UI components:** Display reports, metrics, resource information, and user feedback states.
* **Types:** Describe report data and the values components can safely consume.
* **Mock provider:** Returns predictable local fixture data.
* **API provider:** Will retrieve real reports after the API contract is verified.
* **Formatting utilities:** Format metrics and handle missing values consistently.

The intended data flow is:

Sanity Studio tool → Dashboard components → Data provider → Mock data or Sitebeacon API.

Components should depend on a shared provider interface rather than directly calling API endpoints.

### Suggested Structure

Adapt this structure to the files generated by the Sanity plugin scaffold. Do not duplicate existing scaffold files unnecessarily.

* `src/index.ts` — Public plugin entry point.
* `src/plugin.ts` — Plugin registration, if separated from the entry point.
* `src/tool/` — Custom Studio tool.
* `src/components/` — Reusable dashboard components.
* `src/types/` — Report and metric types.
* `src/providers/` — Provider interface and implementations.
* `src/mock/` — Mock fixtures.
* `src/utils/` — Formatting and data-mapping utilities.
* `src/__tests__/` — Tests, following the project's chosen test conventions.
* `README.md` — Project documentation.
* `AGENTS.md` — Instructions for coding agents.

## 5. Implementation Plan

### Phase 1: Environment and Scaffold

* Confirm the Node.js version supported by the selected Sanity and plugin-tooling versions.
* Inspect the generated plugin package and available scripts.
* Create or verify the separate development Studio.
* Connect the local plugin to the Studio using the supported local development workflow.
* Confirm the Studio can load the plugin before implementing the dashboard.

### Phase 2: Register the Studio Tool

* Register a tool named `sitebeacon-analysis`.
* Display it as Sitebeacon Analysis in Studio navigation.
* Render a simple placeholder component.
* Verify package resolution, exports, TypeScript, and hot reload.

### Phase 3: Define the Data Contract

* Inspect the provided sample report data.
* Model only fields supported by the available evidence.
* Represent genuinely nullable metrics as nullable types.
* Handle missing properties separately from explicitly null values when necessary.
* Preserve meaningful status values.
* Avoid assigning undocumented meanings to abbreviated field names.
* Add fixtures representing both typical and incomplete reports.

### Phase 4: Implement Mock Data

* Define a shared data-provider interface.
* Implement a local mock provider.
* Support retrieving the report list and an individual report.
* Add fixtures for successful, poor-scoring, incomplete, pending, and failed reports where the data model supports these states.
* Keep fixture data out of production API logic.

### Phase 5: Build the Dashboard

Implement the UI incrementally:

1. Dashboard layout and summary cards.
2. Desktop and mobile comparisons.
3. Lab and field metrics supported by the data.
4. Accessibility and resource information.
5. Report listing and report-detail views.
6. Search, filtering, pagination, and refresh where appropriate.

Keep components focused and reusable. Avoid building the entire dashboard in one large component.

### Phase 6: Handle Edge Cases

Test and implement:

* Initial loading.
* Empty report lists.
* No matching search results.
* Provider or API errors.
* Partial reports and missing metrics.
* Pending and failed reports.
* Long URLs and large result sets.
* Repeated refreshes and changing report selections.

Do not display fabricated scores or silently treat missing data as zero.

### Phase 7: Testing

* Run the available lint and TypeScript checks.
* Test metric formatting and data mapping.
* Test provider behavior.
* Test important dashboard states.
* Test the Studio tool in the development Studio.
* Verify the production package build.
* Add or extend automated tests using the repository's existing test setup.

Do not claim a check passed unless it was actually run successfully.

### Phase 8: Real API Integration

Before implementation, verify:

* Base URL and endpoint definitions.
* Report-list and report-detail response shapes.
* Authentication and authorization.
* Pagination and filtering semantics.
* Rate limits and timeout expectations.
* Error responses and retry behavior.
* Nullable and optional fields.
* Whether the API supports desktop/mobile and historical reports.

Implement the real provider behind the same interface as the mock provider.

Never expose private API credentials in browser-accessible Studio code or public environment variables. If a secret is required, use an appropriately secured backend or proxy.

### Phase 9: Documentation and Release

* Complete the README.
* Document configuration and required environment variables.
* Document development and test commands based on actual package scripts.
* Verify exports, generated files, dependency declarations, and peer dependencies.
* Run available validation and build commands.
* Check that no credentials, local paths, or private test data are included.
* Follow the current Sanity plugin publishing process.

## 6. Engineering Principles

### Separation of Concerns

Keep UI rendering, data retrieval, formatting, and type definitions separate. This improves testability and makes future API changes easier to manage.

### Mock-First Development

Develop against predictable fixtures before integrating the real API. This reduces dependency on external services and makes edge cases easier to reproduce.

### Explicit Data Contracts

Types should reflect verified data rather than assumptions. Use appropriate optional and nullable types, and validate untrusted API responses at the integration boundary when needed.

### Single Responsibility

Prefer small components and functions with clear purposes. Avoid components that fetch data, transform it, format it, and render every dashboard section at once.

### Safe Missing-Data Handling

A missing metric is not the same as a score of zero. Display unavailable values clearly and preserve the distinction between missing, null, pending, and failed data where meaningful.

### Security by Design

Do not commit secrets, expose private credentials to the browser, or trust API input without appropriate validation. Use least-privilege access and appropriate error handling.

### Reuse Existing Conventions

Inspect the generated scaffold, existing dependencies, scripts, formatting rules, and test setup before introducing new tools or reorganizing files.

### Small, Verifiable Changes

Implement one phase at a time. After each meaningful change, run the relevant checks and confirm the behavior before proceeding.

### Production Readiness

Consider accessibility, error handling, loading behavior, maintainability, dependency compatibility, package exports, and documentation—not just whether the dashboard looks correct locally.

## 7. Coding-Agent Workflow

Before changing code:

1. Inspect the relevant files and current repository state.
2. Read the applicable README and AGENTS.md instructions.
3. Identify existing conventions and the smallest appropriate change.
4. Explain significant assumptions or decisions when they affect the implementation.

While changing code:

1. Preserve existing behavior unless a change is required.
2. Avoid unnecessary dependencies and unrelated refactors.
3. Do not invent API endpoints, response fields, or authentication rules.
4. Keep TypeScript types accurate and avoid unnecessary `any` casts.
5. Follow the repository's established naming and formatting conventions.

After changing code:

1. Run relevant lint, type-check, test, and build commands when available.
2. Report which checks were run and their actual results.
3. Explain any unresolved issues or unverified behavior.
4. Summarize changed files and the reason for each significant change.

Do not claim the plugin is production-ready while required integration, security, or validation work remains incomplete.

## 8. Definition of Done

A feature is complete when:

* Its behavior matches the agreed requirement.
* Its data contract is clear.
* Missing and error cases are considered.
* Relevant checks have been run.
* No unrelated changes or secrets have been introduced.
* The documentation is updated when behavior, configuration, or workflows change.

The plugin is ready for an initial release only when the package builds correctly, the documented installation works, the intended behavior is tested, and known limitations are clearly documented.
